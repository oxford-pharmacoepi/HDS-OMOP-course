From reports to apps

In Quarto we rendered a report with fixed plots and tables. A Shiny app lets someone interact with the results. They can choose a database, change a filter, or switch between plots, and the displayed output can update.

A Shiny app has a user interface and a server function. We will keep them in separate files, matching the structure that OmopViewer generates:

  • ui.R defines the ui object: the controls someone can use and the spaces where outputs will appear.
  • server.R defines the server function that reads those inputs and creates the outputs.

When an input changes, Shiny updates the outputs that depend on it. This is reactivity.

Here, “server” means a function in our R code. Both files form one app, which can run on your own computer.

Your first Shiny app

Reopen practical.Rproj after the OmopStudyBuilder session. In RStudio, choose File → New File → Shiny Web App…, name the app first-shiny, and select a multiple-file app.

Click Run App and move the slider in the starter histogram example. What changes?

RStudio creates first-shiny/ui.R and first-shiny/server.R. Shiny reads both files when it starts the app.

Install shiny and bslib if RStudio reports that either is missing.

The app keeps your R session busy while it runs. Click Stop in RStudio before running other code or restarting the app.

The UI: what goes where?

Replace the contents of first-shiny/ui.R with:

library(shiny)

ui <- fluidPage(
  titlePanel("Hello Shiny!"),
  sidebarLayout(
    sidebarPanel(
      sliderInput("bins", "Number of bins:",
                  min = 1, max = 50, value = 30)
    ),
    mainPanel(plotOutput("distPlot"))
  )
)

bins is the slider’s ID. distPlot is the space where the server will put the plot. These IDs connect the two parts of the app.

The server: make the plot

Replace the contents of first-shiny/server.R with:

library(shiny)

server <- function(input, output, session) {
  output$distPlot <- renderPlot({
    x <- faithful$waiting
    bins <- seq(min(x), max(x), length.out = input$bins + 1)
    hist(x, breaks = bins, col = "steelblue", border = "white",
         xlab = "Waiting time to next eruption (minutes)",
         main = "Old Faithful")
  })
}

faithful is a built-in dataset; the histogram groups its waiting times into bins. input$bins reads the slider, and output$distPlot sends the plot to the UI.

Just as $ picked a table column in R, here it picks a named input or output. renderPlot() reruns when the slider value changes.

Give the UI a style with bslib

bslib gives us layouts, cards, sidebars, and themes. Replace the contents of ui.R with this code and leave server.R unchanged:

library(shiny)
library(bslib)

ui <- page_sidebar(
  title = "My first app",
  theme = bs_theme(bootswatch = "flatly"),
  sidebar = sidebar(
    sliderInput("bins", "Number of bins:",
                min = 1, max = 50, value = 30)
  ),
  card(plotOutput("distPlot"))
)

Save ui.R and click Run App again. The IDs still connect the slider in ui.R to the plot created in server.R.

Meet OmopViewer

Building every filter, table, and plot by hand takes time. OmopViewer creates a multiple-file Shiny app for us from supported OMOP study results.

It generates separate UI, server, and setup files. We can then make small changes to fit our study.

Two ways to use it:

  • launchDynamicApp(): quickly inspect uploaded results without creating an app project.
  • exportStaticApp(): generate a persistent set of app files that we can inspect, edit, and share.

What data does it need?

OmopViewer works with summarised_result objects: summary estimates together with settings that describe the analyses that produced them.

The settings help OmopViewer choose the appropriate panels for supported result types.

For this exercise, we will use cohort attrition and characteristics results from the reporting training, for amoxicillin and metformin.

Attrition shows how cohort counts change as criteria are applied. Characteristics describe the people in the cohorts, such as their ages. We will learn to produce these results later in the course.

Download OmopViewer results for this exercise. The four-column Data 1 and Data 2 files from the Quarto session are ordinary tables and cannot be used directly here.

Import the results in R

Stop the dynamic app and return to omopviewer.R.

library(OmopViewer)
library(omopgenerics)
library(here)
library(shiny)

result <- importSummarisedResult(
  here("data", "omopviewer_results.csv")
)
settings(result)

Use importSummarisedResult() to restore the results and their settings. read_csv() alone does not reconstruct this object.

Export an app we can edit

exportStaticApp(
  result = result,
  directory = here("viewer"),
  title = "My study results",
  background = TRUE,
  summary = TRUE,
  open = FALSE
)

runApp(here("viewer", "shiny"))

OmopViewer creates a shiny folder inside viewer. Here, “static” means the results are supplied when we generate the app; the app itself is still interactive and needs R to run.

What did OmopViewer create?

Stop the app, then open viewer/shiny in RStudio’s Files pane.

For this exercise, keep practical as the active R Project. Browse the files without opening the generated shiny.Rproj, so the here() paths in our script stay the same.

File What to look for
global.R Packages and data loaded for the app.
ui.R Layout, panels, labels, and input controls.
server.R Code that responds to inputs and builds outputs.
functions.R Helper functions used by the UI and server.
background.md Text for the background panel.
rawData/ and data/ Original results, preparation code, and prepared app data.

Start with the export options

Before editing the generated files, try changing the title and hiding the summary panel:

exportStaticApp(
  result = result,
  directory = here("viewer_custom"),
  title = "Exploring our cohorts",
  background = TRUE,
  summary = FALSE,
  open = FALSE
)

runApp(here("viewer_custom", "shiny"))

We use a second folder so we can compare the two apps. There are also options for themes, logos, and organising panels.

YOUR TURN Make it yours

Stop the app and work in viewer_custom/shiny:

  1. Edit background.md: add a heading and two sentences explaining what someone can explore.
  2. Open ui.R. Find a visible label and change its text. Keep input and output IDs the same so their connections still work.
  3. Find the corresponding input or output in server.R. Can you follow what it does?
  4. Run the app again and check your changes.
runApp(here("viewer_custom", "shiny"))

Save your edits before restarting. Exporting again to the same location can overwrite the generated app, so use a new folder if you want to keep your manual changes.

If the app does not start

  • R is still busy: stop the previous app before running more code.
  • Result object not found: rerun the import step in omopviewer.R.
  • Cannot find a file: check that practical is still the active project and that you saved the correct CSV in data.
  • Package missing: install the named package in the active project’s library, then try again.

If a small edit breaks the app, undo that edit and restart. Check labels and IDs carefully; changing the displayed text should not change the connection between UI and server.

How does this fit into a study?

In our exercise, OmopViewer exports to viewer/shiny inside the practice project. OmopStudyBuilder’s studyShiny folder is a place to organise the reporting app for a real study; the tools do not automatically connect these two folders.

Later, the analysis code will produce the summary results that we import here.

Running an app on your computer does not publish it for everyone else. Sharing the app files and hosting an app online are separate steps; deployment is beyond today’s exercise.

Final remarks

  • Shiny: ui.R collects inputs and displays outputs; server.R connects them with R code.
  • OmopViewer: creates the app structure and result panels for us.
  • Use the dynamic viewer to explore, or export an app when you want to customise it.

Start with a small change, run the app, and see what happens :)
