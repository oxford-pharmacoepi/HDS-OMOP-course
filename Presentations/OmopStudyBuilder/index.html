Why OmopStudyBuilder?

We have seen how an R Project keeps our work together and how GitHub helps us share it. Now imagine several teams running the same study in different OMOP databases.

It helps if everyone knows where to find the code, the instructions, and the results.

OmopStudyBuilder gives us a common starting structure for study projects and repositories. We add the study-specific code and documentation.

What will we do?

  1. Create the study structure with initStudy().
  2. Explore the generated files and create a private repository on GitHub.
  3. See how renv records the packages a project uses.
  4. Use reviewStudy() to get an overview of the code and dependencies.

The package also has Docker tools for running studies in containers. Today we will focus on setting up and reviewing a study.

Create a study

Reopen practical.Rproj. Choose a new folder beside it, replacing yourusername with your GitHub username:

library(OmopStudyBuilder)
library(here)

study <- "hds-study-yourusername"
initStudy(
  directory = file.path(dirname(here()), study),
  studyTitle = "My HDS practice study",
  studyLeads = "Your name",
  studyDescription = "Practising a shared OMOP study structure.",
  repository = study,
  organisation = "oxford-pharmacoepi",
  private = TRUE
)

The destination must be new or empty. Let initStudy() create its contents before opening any of the generated R Projects.

dirname(here()) finds the folder containing your current project; file.path() builds the path to the new study folder.

Unlike the first public practice repository, this study repository is private. Only people and teams given access can view or clone it. private = TRUE makes that choice explicit, although it is also the function’s default.

What did it create?

hds-study-yourusername/
├── README.md
├── INSTRUCTIONS.md
├── diagnosticsCode/
├── diagnosticsShiny/
├── studyCode/
└── studyShiny/
  • diagnosticsCode: diagnostics of phenotypes.
  • studyCode: run the study analyses.
  • diagnosticsShiny and studyShiny: places for apps that explore the results.

Both diagnostics and study default to TRUE. Set either to FALSE in initStudy() if you do not need that pair of folders.

One repository, several R Projects

Each of the four component folders contains an .Rproj file. Open the project for the part you are working on.

For example, open studyCode/studyCode.Rproj for the main analysis. In that session, here() points to studyCode, not the whole repository.

This still follows our “one project for one piece of work” approach: the repository groups several separate components together.

File or folder inside studyCode What goes there?
codeToRun.R The entry script, including database-specific settings.
runStudy.R The sequence of study steps.
codelist/ and cohorts/ Code to define the study population.
analyses/ Code for the analyses.
Results/ Output from the study.

  2. Read the root README.md and INSTRUCTIONS.md. Which parts would you update for a real study?
  3. Open studyCode/studyCode.Rproj, then look at codeToRun.R and runStudy.R.
  4. Find where you would add cohort definitions and an analysis.

For now, explore the scripts rather than sourcing them: the database connection and study-specific code are still to be filled in.

Keep the instructions with the code

In the root README, write a short description of your practice study. For example: which population would you study, and what would you measure?

Then use the workflow from the GitHub session:

  • Create a branch for your changes.
  • Commit and push them.
  • Open a pull request and ask a colleague whether the instructions are clear.

After merging, switch to main in Desktop and Fetch origin → Pull origin to update your local copy.

Why use renv?

The same code can behave differently when people have different package versions. renv gives an R Project its own package library and records package versions in renv.lock.

  • The study developer prepares the environment and records it.
  • A colleague restores that environment when they run the study.
  • The lockfile is committed alongside the code, so changes can be reviewed in GitHub.

The generated study folders do not yet contain a lockfile. Prepare renv in each component R Project that you use, after deciding which packages its code needs.

renv: the basic workflow (demo)

Watch this first; setting up the full template’s packages can take time. Open studyCode/studyCode.Rproj, install renv if needed, and initialise it once:

install.packages("renv")
library(renv)
init()

init() scans the project and prepares its package library and lockfile. It may need to install packages referenced by the template.

Function When would we use it?
snapshot() Record the package versions after changing and checking the code.
restore() Install the versions recorded in an existing lockfile.
status() Check whether the project library and lockfile agree.
activate() Activate renv in a project.
deactivate() Deactivate renv in a project.

Commit renv.lock and the activation files created by renv; its .gitignore excludes the local package library. renv records the R version but does not install R itself.

Get an overview with reviewStudy()

Before sharing code with a data partner, it is useful to see what is in the project.

From the studyCode R Project, install OmopStudyBuilder there if it is missing from your new renv library, then run:

library(OmopStudyBuilder)
library(here)

reviewStudy(dir = here(), dependencies = FALSE)

This prints a summary of the R scripts and JSON, CSV, and Excel files. dependencies = FALSE lets everyone try it, including those who have not set up renv yet.

It gives us a starting point for review; we still need to read the code and check that it answers the study question.

Review the dependencies too

Once studyCode/renv.lock exists, run:

reviewStudy(dir = here(), type = "analysis")

By default, both code and dependencies are TRUE. The dependency review uses the lockfile and reports on package versions and sources.

For a reporting or app project, open that component’s R Project and use type = "reporting".

Run the review in the component folder containing the lockfile. A review of the repository root will not automatically review every component’s environment.

YOUR TURN Review your study

  1. Run reviewStudy(dir = here(), dependencies = FALSE) from studyCode.
  2. Find the entry script and the analysis scripts in the output. Which are still empty?
  3. If you have prepared a lockfile, run the dependency review too. Pick one package and find its recorded version.
  4. Add a note to your pull request, or a new issue if it has already been merged, describing what still needs to be completed before the study can run.

Discuss the review with your colleague. A common folder structure makes it easier to find things, but the code and instructions still need a human review.

Final remarks

  • Start with initStudy() so everyone recognises the study layout.
  • Keep the instructions and code together in GitHub.
  • Use renv to record and restore package versions.
  • Use reviewStudy() to help you inspect the project before sharing it.
